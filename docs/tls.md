# ノード間 TLS（相互認証）

ノード間の RPC（Raft、ブロックの転送）は、相互認証つきの TLS 1.3 にできます。設定方法は次の 2 つです。

- **証明書を自動で発行する（推奨）**：内部 CA を 1 度作れば、各ノードの証明書は起動時に自動で用意されます。
- **鍵ストアを自分で用意する**：`SCALAS3_TLS_KEYSTORE` などで指定します（下の「手動で用意する」）。

## 自動で発行する

### 1. 内部 CA を作る

```bash
scalas3 cert init-ca --dir ./scalas3-ca
```

`ca.crt`（CA の証明書）、`ca.key`（CA の秘密鍵）、`join.secret`（参加の秘密）を作り、参加トークン（`S3J1.…`）を表示します。`ca.key` と `join.secret` は所有者だけが読めるように書きます。

### 2. 初期メンバーを起動する

初期メンバーには CA のディレクトリを置き、`SCALAS3_TLS_CA_DIR` を設定します。

```bash
SCALAS3_TLS_CA_DIR=/etc/scalas3/ca ...
```

各ノードは、起動時に自分の鍵と証明書を作り、CA で署名します。結果はデータディレクトリの `tls/` に置き、次の起動からはそれを使います。

さらに、後から加わるノードのために、参加の受け付け（HTTPS、既定は `0.0.0.0:3902`、`SCALAS3_JOIN_LISTEN` で変更）を開きます。

### 3. 後から加わるノード

参加トークンと、CA を持つノードの参加の受け付けのアドレスを渡します。CA の鍵は渡しません。

```bash
SCALAS3_JOIN_TOKEN='S3J1.…' SCALAS3_JOIN_ADDRESS=10.0.0.1:3902 SCALAS3_BOOTSTRAP=false ...
```

ノードは鍵を作り、署名要求を参加の受け付けに送って証明書を受け取ります。受け取った証明書はデータディレクトリの `tls/` に置き、次の起動からはそれを使います（トークンは使わなくなります）。

### 安全性

- **相手の確認**：参加トークンには CA の証明書の SHA-256 が入っています。参加するノードは、受け付けが同じ CA の証明書を示したときだけ信頼します。なりすましの受け付けに秘密を渡しません。
- **秘密の確認**：受け付けは、トークンの秘密が一致したときだけ署名します。
- **名前の扱い**：証明書の名前（CN と SAN）は、要求側が書いた名前ではなく、送られてきたノード ID にします。
- **有効期間**：ノードの証明書は 3 年（`SCALAS3_TLS_CERT_DAYS` で変更）、CA は既定で 10 年です。ノードの証明書は自動で更新します（下の「証明書の更新」）。CA の更新はありません。期限が近づいたら CA を作り直し、全ノードの `tls/` を消して起動し直してください。
- **秘密が漏れたら**：参加の秘密が漏れた場合は、`join.secret` を新しい値に替え、CA を持つノードを起動し直してください。CA を作り直さなくても、新しいトークンにできます。新しいトークンは、`S3J1.<新しい秘密>.<ca.crt の SHA-256>` の形です。
- **ネットワーク**：参加の受け付けは、クラスタの内側のネットワークからだけ届くようにしてください。

### 証明書の更新

各ノードは 6 時間ごとに自分の証明書を見て、有効期間の 2/3 を過ぎていれば（3 年なら残り 1 年）新しい鍵で発行し直します。

- **CA を持つノード**：自分で発行し直します。
- **後から加わったノード**：いまの証明書で相互認証して、参加の受け付けの `/v1/renew` に署名要求を送ります。参加トークンは要りません。
  受け付けは、クラスタの CA が発行した期限内の証明書を示したノードにだけ、その証明書と同じ名前で発行します。
  受け付けのアドレスは、参加したときに `tls/join-address` に保存したものを使います（`SCALAS3_JOIN_ADDRESS` があればそちら）。
- **読み直し**：書き換えた鍵ストアは、TLS の層が 1 分以内に読み直し、新しい接続から使います。張ったままの接続はそのまま使います（証明書の期限はハンドシェイクのときにしか確かめません）。
- **失敗したとき**：警告をログに出し、次の確認でもう一度試します。期限が切れてしまった後は更新できません。そのノードの `tls/` を消し、参加トークンでもう一度参加させてください。
- **取り外したノード**：失効の仕組み（CRL）はありません。取り外したノードの証明書は期限まで有効で、そのノードは受け付けで更新もできます。
  ノードを取り外すときは、受け付けに届かないようにネットワークで閉じてください。漏れた疑いがあるときは、CA を作り直してください。

## 手動で用意する

全ノードで同じ自己署名の鍵ストアを使う、いちばん簡単な方法です。

```bash
scalas3 cert create --out cluster.p12 --password '…'
SCALAS3_TLS_KEYSTORE=cluster.p12 SCALAS3_TLS_PASSWORD='…' ...
```

自分の CA で発行した鍵ストアを使う場合は、`SCALAS3_TLS_TRUSTSTORE` に CA の証明書の入ったトラストストアを指定します。

鍵ストアとトラストストアは 1 分ごとに更新時刻を見て、変わっていれば読み直します。差し替えるときは、別の名前で書いてから mv で置き換えてください（書きかけのファイルを読むと、警告を出して前のものを使い続けます）。

## 公開ポートの HTTPS

ここまではノード間の通信の話です。S3 の公開ポートも、前段にリバースプロキシを置かずに HTTPS で受けられます（既定の Netty のサーバーのときだけ）。

```bash
SCALAS3_S3_TLS_CERT=/etc/letsencrypt/live/s3.example.com/fullchain.pem \
SCALAS3_S3_TLS_KEY=/etc/letsencrypt/live/s3.example.com/privkey.pem \
java -jar scalas3-server.jar
```

- **証明書**：PEM で、サーバーの証明書、中間 CA の順に並べた鎖（Let's Encrypt の `fullchain.pem`）。
- **秘密鍵**：PEM で、形式は問いません（PKCS#8、RSA の PKCS#1、EC の SEC1）。パスフレーズ付きの鍵は読めません。
- **自動の読み直し**：1 分ごとにファイルの更新時刻を見て、変わっていれば読み直します。新しい接続から新しい証明書を使います。
  - 読み直しに失敗したとき（壊れたファイル、鍵と証明書が対になっていない更新の途中など）は、前の証明書を使い続けて警告を出します。
  - 鍵と証明書のどちらかが後から更新されれば、その時点でもう一度読みます。
- **プロトコル**：TLS 1.2 と 1.3 だけを受けます。HTTP/2 には対応していません（HTTP/1.1 のみ）。
- **`aws:SecureTransport`**：直接つないだ接続が HTTPS なら、バケットポリシーの `aws:SecureTransport` は true になります。
- **設定ファイル**では `s3.tls.cert` と `s3.tls.key`。
