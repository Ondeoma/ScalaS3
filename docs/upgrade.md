# アップグレード

scalas3 は、ノードを 1 台ずつ新しい版に入れ替える（ローリングアップグレード）ことで、止めずに更新できます。

## 手順

1. 全ノードが動いていて、Admin API の `/v1/status` で互いに `up: true` になっていることを確かめます。
2. 1 台を止めます（SIGTERM。コンテナなら `stop`）。データのディレクトリ（またはボリューム）はそのまま残します。
3. 同じデータのディレクトリと同じ設定で、新しい版を起動します。
4. そのノードが S3 に答えるようになり（`/v1/health`）、ほかのノードの `/v1/status` で `up: true` になるまで待ちます。
   さらに、Raft のログに追いつくまで十数秒おきます。
5. 次のノードで 2〜4 を繰り返します。

一度に止めるのは 1 台だけにしてください。メタデータは過半数のノードがそろっていないと書けません（3 ノードなら 2 台）。

ロードバランサーやリバースプロキシの後ろに置いている場合は、止める前にそのノードを外してください（docs/reverse-proxy.md）。外さないと、止めている間にそのノードへ届いた要求が失敗します。

## 版が混ざっている間

入れ替えの途中は、古い版と新しい版のノードが混ざります。

- **データの形式**：ディスクの形式とノード間のメッセージは、1 つ前の版と互換にします（設計 §11）。
- **新しい機能**：古い版が読めない Raft のコマンドを使う機能は、全ノードが新しくなってから自動で有効になります。
  各ノードは死活確認の応答で、対応している機能の水準を伝えます（Admin API の `/v1/status` の `features`）。
  たとえば水準 1（レンジの統合）は、全ノードが水準 1 以上と分かるまで統合を始めません。
- **戻すとき**：入れ替えの途中なら、新しい機能はまだ使われていないので、新しい版にしたノードを古い版に戻せるはずです（試験では確かめていません）。全ノードを新しくした後は、新しい機能が使われ始めるので、古い版に戻さないでください。

## 試験

`it/upgrade/run.sh` は、podman で 3 ノードのクラスタを古い版で動かし、1 台ずつ新しい版に入れ替えて確かめます。

```bash
it/upgrade/run.sh <古い版の git の参照>      # 例：it/upgrade/run.sh v0.9.0（既定は HEAD~1）
```

- 古い版は git worktree に取り出してビルドし、新しい版はいまの作業ツリーからビルドします。どちらもイメージにします。
- 確かめること：
  - 入れ替える前に書いたオブジェクト（インライン、1 ブロック、複数ブロック）が、入れ替えた後も全ノードから同じ中身で読めること。
  - 入れ替えの間も書き込みと読み込みを続け、成功した書き込みが失われないこと。
  - 古い版で始めたマルチパートアップロードを、新しい版で完了できること。
  - 全ノードを止めて新しい版だけで起動し直しても、すべて読めること。
- `KEEP=1` なら、終わった後もコンテナとボリュームを残します。`SKIP_BUILD=1` なら、作ってあるイメージを使います。
