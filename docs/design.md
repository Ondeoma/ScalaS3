# scalas3 設計書

- ステータス: ドラフト v0.1

---

## 1. 概要

scalas3 は、Scala 3、cats-effect 3、fs2、http4s で実装する、S3 互換の分散オブジェクトストレージです。

- **位置づけ**: Ceph と Garage の中間を狙います。Ceph より導入と運用が簡単で、Garage より強い一貫性と豊富な S3 機能を持たせます。
- **構成**: 1 台から N 台（〜10 ノード程度）まで組めます。1 台は単体で動かし、3 台以上で高可用性（HA）になります。
- **ライセンス**: MIT の OSS として公開します。

### 1.1 目標

| # | 目標 |
|---|---|
| G1 | 主要な S3 API を互換にし、公式の AWS SDK からも問題なく使えるようにする |
| G2 | メタデータを強一貫性（線形化可能）にする。書き込んだ直後に読み込むと必ずその内容が見える |
| G3 | データをレプリケーションとイレイジャーコーディング（EC）で冗長化する。ストレージクラス単位、バケット単位で選べるようにする |
| G4 | ノードを動的に追加・削除でき、自動でリバランスする。ゾーンを考慮して配置する |
| G5 | 外部のデータベースや合意基盤に依存しない。JVM 以外で必要なネイティブライブラリもない |
| G6 | Garage や MinIO と比べて遜色のない性能を出す |
| G7 | 決定的シミュレーションで正しさを検証できる設計にする |

### 1.2 非目標（v1.0 では対象外）

- Web 管理 UI（Admin API を OpenAPI で定義しておき、後から載せられるようにします）
- 拠点（WAN）をまたいで強一貫性を保つこと（拠点間はクラスタ同士の非同期複製で対応します）
- IAM と完全に互換にすること（ユーザー、ロール、STS）
- S3 Select、Object Lock、Glacier 系のストレージクラス、SigV2
- 数百ノードを超える規模や、PB を超える規模

## 2. 要件の整理

### 2.1 規模の想定

| 項目 | 想定値 |
|---|---|
| ノード数 | 1〜10（それ以上も動くようにはするが、最適化はしない） |
| 総容量 | 〜数十TB |
| オブジェクト数 | 〜数千万件 |
| 1 ノードのディスク | JBOD で複数台。メタデータ用に SSD を分けられる |
| ネットワーク | 同一の DC または LAN 内（RTT 1ms 未満） |

### 2.2 v1.0 で対応する S3 API

**バケット**
- CreateBucket、DeleteBucket、HeadBucket、ListBuckets、GetBucketLocation
- Put/Get/DeleteBucketVersioning
- Put/Get/DeleteBucketCors
- Put/Get/DeleteBucketPolicy
- Put/Get/DeleteBucketLifecycleConfiguration
- Put/Get/DeleteBucketEncryption
- Put/Get/DeleteBucketReplication

**オブジェクト**
- PutObject、GetObject（Range 指定、条件付きリクエスト）、HeadObject
- DeleteObject、DeleteObjects
- CopyObject
- ListObjects（V1）、ListObjectsV2、ListObjectVersions
- 条件付き書き込み（`If-None-Match: *`、`If-Match`）

**マルチパートアップロード**
- CreateMultipartUpload、UploadPart、UploadPartCopy
- CompleteMultipartUpload、AbortMultipartUpload
- ListMultipartUploads、ListParts

**認証**
- SigV4（ヘッダー認証、Presigned URL）
- ストリーミング署名: `STREAMING-AWS4-HMAC-SHA256-PAYLOAD`、`*-TRAILER` 系、`UNSIGNED-PAYLOAD`
- 追加チェックサム: `x-amz-checksum-{crc32,crc32c,crc64nvme,sha1,sha256}`（ヘッダーとトレーラーの両方）

> 最近の AWS SDK は、標準でトレーラー付きのチェックサムを送ってきます。そのため、チェックサム対応は必須として扱います。

**暗号化**
- SSE-C、SSE-S3

**アドレス指定**
- パス形式（path-style）と仮想ホスト形式（virtual-host style）の両方に対応します。

## 3. 全体アーキテクチャ

```
                 S3 クライアント (AWS SDK / rclone など)
                                   │ HTTPS
          ┌────────────────────────┼─────────────────────────┐
          ▼                        ▼                         ▼
  ┌───────────────┐        ┌───────────────┐         ┌───────────────┐
  │    Node A     │        │    Node B     │         │    Node C     │
  │ ┌───────────┐ │        │ ┌───────────┐ │         │ ┌───────────┐ │
  │ │ S3 API    │ │        │ │ S3 API    │ │         │ │ S3 API    │ │  ← http4s (Ember)
  │ │ Admin API │ │        │ │ Admin API │ │         │ │ Admin API │ │  ← tapir + OpenAPI
  │ ├───────────┤ │        │ ├───────────┤ │         │ ├───────────┤ │
  │ │ Gateway   │ │        │ │ Gateway   │ │         │ │ Gateway   │ │  ← 認証・認可、書き込みと読み込みの調整
  │ ├─────┬─────┤ │        │ ├─────┬─────┤ │         │ ├─────┬─────┤ │
  │ │Meta │Block│ │        │ │Meta │Block│ │         │ │Meta │Block│ │
  │ │Multi│Store│ │◄──────►│ │Multi│Store│ │◄───────►│ │Multi│Store│ │  ← 独自 RPC (fs2 TCP + mTLS)
  │ │Raft │     │ │        │ │Raft │     │ │         │ │Raft │     │ │
  │ ├─────┤     │ │        │ ├─────┤     │ │         │ ├─────┤     │ │
  │ │LSM  │JBOD │ │        │ │LSM  │JBOD │ │         │ │LSM  │JBOD │ │
  │ └─────┴─────┘ │        │ └─────┴─────┘ │         │ └─────┴─────┘ │
  └───────────────┘        └───────────────┘         └───────────────┘
```

- **全ノードが対等**です。どのノードも S3 リクエストを受け付けます。役割を分けたノード（ゲートウェイ専用、ストレージ専用）は v1.0 では作りません。
- **メタデータ層**: キー空間をレンジ単位に分割し、レンジごとに Raft グループを作ります（Multi-Raft）。各ノードは自前の LSM-Tree に状態を保存します。
- **データ層**: オブジェクトを固定長のブロックに分け、内容のハッシュで識別します。ブロックは配置アルゴリズムで決めたディスクに、レプリカまたは EC 断片として直接書き込みます。**データは Raft を通しません。**
- **整合性の境界**: 「ブロックがディスクに永続化された」**後で**メタデータを Raft でコミットします。これで、コミット済みのメタデータが指すブロックは必ず存在することになります。

### 4.1 実装方針

- **ドメインロジックは純粋関数にします。** Raft のコアは `step(state, input) => (state, outputs)` の形にします（etcd/raft の設計に倣います）。LSM のマージやコンパクションの選び方、配置計算も同様に副作用を持たせません。
- **副作用は capability trait 経由で扱います。** 時計、ネットワーク、ディスク、乱数は `runtime` の trait（`Clock`、`Transport`、`FileSystem`、`Random`）を通してのみ使います。`IO.realTime`、`java.nio`、`System.nanoTime` をドメインのコードから直接呼ぶことは、lint で禁止します。
- **エフェクトの型**: `IO` を直接使い、依存先は trait で差し替えます。tagless final は使いません。決定的に動かすことは、`TestControl` と sim 用の実装で保証します。
- **native-image への配慮**: リフレクションや実行時のコード生成に頼るライブラリは使いません。サーバーの native-image ビルドが通ることを CI で確認します（ただし配布の主力は JVM です）。

## 5. メタデータ層

### 5.1 キー空間とレンジ

メタデータは、**辞書順に並んだ 1 つのキー空間**として扱います。このキー空間を連続した区間に区切り、それぞれを**レンジ**と呼びます。

- 各レンジは独立した Raft グループで複製します。複製数は既定で 3（設定で 5 も可）、1 ノード構成では 1 です。
- レンジは大きさや負荷に応じて**分割**し、小さくなれば**統合**します。
  - 分割の目安は 64MiB です。統合は、隣り合う 2 つのレンジの中身の合計が 2MiB 以下になったときに行います（§17「レンジの統合」）。
- **分割点は、オブジェクトキーの境目に限ります。** つまり、1 つのオブジェクトキーに関係するレコード（現在の版、全バージョン、マルチパートの状態）は、必ず同じレンジに入ります。これにより、オブジェクト単位の操作は**単一レンジ内のアトミックなバッチ**で済みます。

**システムレンジ（レンジ 0）** は特別扱いで、次の情報を持ちます。

- クラスタの設定、レイアウト（ノード、ディスク、ゾーン、重み）
- レンジの記述子（どのキー区間を、どのノードが担当するか）
- アクセスキー、バケットの定義（バケットの数は少ないので、まとめてここに置きます）

### 5.2 キーのエンコード

キーの順序を保つエンコードを使います。可変長のバイト列は `0x00` を `0x00 0xFF` にエスケープし、末尾を `0x00 0x01` で終端します。

```
テーブル ID
  0x01 RangeLocal   : [0x01][rangeId u64][種別][...]        ← レンジ固有。そのレンジの Raft で複製する
                        種別 = AppliedIndex | Outbox[seq] | Lifecycle[dueTime][bucketId][objKey*][versionId]
  0x02 System       : [0x02][種別][...]                    ← レンジ 0
  0x10 Objects      : [0x10][bucketId u64][objKey*][subtag][...]
  0x20 BlockRefs    : [0x20][storageClass u16][blockHash 32B][bucketId][objKey*][versionId]

Objects の subtag:
  0x00              : Head        … 現在の版を指すポインター（最新の versionId、削除マーカーかどうか）
  0x01 [~versionId] : Version     … バージョンのレコード（新しい順に並ぶよう、versionId をビット反転）
  0x02 [uploadId]   : Upload      … マルチパートアップロードの状態
  0x03 [uploadId][partNo u32] : Part
```

- RangeLocal のキーは、オブジェクトのレコードと**同じ Raft バッチ**で書けます。レンジを分割するときは、Outbox と Lifecycle のエントリーを、含まれるオブジェクトキーに従って新しいレンジに振り分けます。
- `bucketId` はバケットを作るたびに新しく採番します。そのため、同じ名前のバケットを削除して作り直しても、古いデータとは混ざりません。
- **ListObjectsV2** は `[0x10][bucketId][prefix]` から走査し、Head を読んだら Version と Upload は seek で飛ばします。バージョンが大量にあっても、一覧の速度が落ちにくくなります。

### 5.3 レコードの主な内容

```scala
final case class ObjectVersion(
  versionId:    VersionId,          // HLC ベース。バージョニングが無効なら "null" 版を上書きする
  isDeleteMarker: Boolean,
  size:         Long,
  etag:         ETag,
  lastModified: HlcTimestamp,       // リーダーが提案に含めた時刻（適用は決定的に行う）
  contentType:  String,
  userMeta:     Map[String, String],
  checksums:    Checksums,          // CRC32C 等（クライアントが送ってきた場合）
  storageClass: StorageClassId,
  encryption:   Option[EncryptionInfo],
  body:         Body                // Inline(bytes) | Blocks(Vector[BlockRef]) | Parts(...)
)
```

### 5.4 Raft の実装

CE3 で自前実装します。

- **コア**は純粋な状態マシンです。入力（受信メッセージ、tick、提案、永続化の完了）を受け取り、出力（送信メッセージ、永続化の要求、適用するエントリー、提案への応答）を返します。
- **機能**:
  - リーダー選出: PreVote、CheckQuorum
  - ログの複製: パイプライン化、バッチ化、フロー制御
  - メンバー変更: Joint Consensus。追加するノードは Learner から昇格させます。
  - リーダーの移譲（Leadership Transfer）
  - スナップショットの送受信（ストリーミング）
  - 線形化可能な読み込み: 既定は ReadIndex です。リーダーリースは設定で有効にできる最適化とします（時計のずれに上限があることが前提）。
- **ログの保存（Raft Log Engine）**:
  - ノード内のすべての Raft グループで、**1 本の追記ログ（セグメントファイル）を共有**します。
  - 複数の書き込みをまとめて 1 回の fsync で済ませます（グループコミット）。グループごとに fsync すると遅くなるのを避けるためです。
  - インデックスはメモリ上に持ち、古いセグメントは「全グループが不要になった時点」で消します。
- **提案の中身**: 時刻、`versionId`、条件付き書き込みの前提条件は、**リーダーが決めて提案に含めます**。状態マシンへの適用は完全に決定的に行います。
  - 条件付き書き込み（`If-Match` など）は**適用時に評価**するので、アトミックな CAS になります。

### 5.5 状態マシンとローカル KV の関係

- **1 ノードに 1 つの LSM** を置き、そのノードが担当する全レンジの状態を入れます（TiKV の方式と同じです）。
- コミット済みのエントリーを適用するときは、**変更内容と、そのレンジの `appliedIndex`（RangeLocal キー）を同じバッチで** LSM に書きます。
- **LSM は独自の WAL を持ちません。** クラッシュすると、まだフラッシュしていない memtable は消えます。
  - 再起動したら、フラッシュ済みの `appliedIndex` の次から Raft ログを再生して復旧します。
  - そのため、**Raft ログを切り詰めてよいのは「フラッシュ済みの `appliedIndex`」まで**とします。これは重要な不変条件で、TLA+ で検証します。
- **スナップショット**: レンジのキー区間を LSM の一貫したビューから走査し、ストリームとして送ります。受け取った側は、区間を消したうえで一括で取り込みます（SST を直接取り込む最適化は後で検討します）。

### 5.6 レンジをまたぐ操作

**v1.0 ではレンジをまたぐトランザクション（2PC）を作りません。** レンジをまたぐ必要がある操作は、次の方法で処理します。

| 操作 | 方法 |
|---|---|
| ブロック参照（BlockRefs）の増減 | オブジェクトのレンジで、RangeLocal の **outbox** に「参照の追加・削除」を同じバッチで書きます。レンジのリーダーが outbox を BlockRefs 側のレンジへ冪等に送り、確認できたら消します（トランザクショナル・アウトボックス）。 |
| バケットの削除 | システムレンジでバケットを「削除中」にし、オブジェクトの区間が空であることを確認してから削除を確定します。その間に競合して書き込まれたオブジェクトは、存在しない `bucketId` を指す孤児になります。孤児はバックグラウンドで掃除します。 |
| PutObject で行うバケットの存在確認 | システムレンジを読みます（キャッシュし、世代番号で無効化します）。前の行の掃除で整合性を保ちます。 |
| CopyObject（バケットをまたぐ場合） | コピー元を読み、コピー先にブロック参照を共有した新しいバージョンを書きます。参照は outbox で追加します。 |

**ブロックの GC と重複排除が競合する問題**（「誰も参照していない」と判断して消したブロックを、新しいアップロードが再利用してしまう）は、次のように防ぎます。

1. アップロードするときは、ブロックを書く**前に** BlockRefs に「仮の参照（intent）」を TTL 付きで登録します。
2. GC は「確定した参照も、期限内の intent もない」状態が**猶予期間を過ぎても続いた**ブロックだけを消します。

## 6. データ層（ブロックストア）

### 6.1 ブロック

- オブジェクトの本体を**固定長のブロック**に分割します。既定は 4MiB で、ストレージクラスごとに変えられます。
- **ブロック ID** は `(storageClass, hash(平文 or 暗号文))` です。
  - ハッシュは BLAKE3 と SHA-256 のどちらかを、ベンチマークで決めます。SHA-256 は JDK の intrinsic（SHA-NI）で速くなる可能性があります。
- 同じストレージクラスで同じ内容なら、自動で**重複排除**されます。暗号化したブロックは鍵ごとに暗号文が変わるので、実質的に重複排除の対象外になります。
- ETag 用の MD5 は、ブロックに分ける前のストリームで並行して計算します。

### 6.2 ストレージクラス

```hocon
storage-classes {
  standard { redundancy = replica, copies = 3, write-quorum = 2 }
  ec42     { redundancy = ec, data = 4, parity = 2, write-quorum = 5 }
  single   { redundancy = replica, copies = 1, write-quorum = 1 }   # 1 ノード構成の既定
}
```

- バケットごとに既定のクラスを設定でき、`x-amz-storage-class` ヘッダーでオブジェクトごとにも指定できます（S3 の標準名と独自のクラス名を対応づけます）。
- EC クラスでも、**ブロック 1 つ分に満たない小さなオブジェクト**は、レプリケーションのクラスに自動で切り替えます。EC のオーバーヘッドを避けるためです。

### 6.3 配置（Placement）

- **障害ドメインの階層**: `zone > node > disk`。
  - 1 ノード構成では、自動的に disk を障害ドメインにします。つまり、ディスクをまたいだ複製や EC になります。
- **パーティション**: `partition = hash(blockId) mod P` です。P はクラスタを作るときに固定します（既定 1024）。
- **パーティションからディスク列への対応**は、レイアウトのバージョンから**決定的に計算**します。
  - straw2 に似たハッシュで重みに比例させ、障害ドメインが分散するように制約をかけます（CRUSH の簡略版）。
  - レプリカ i、または EC の断片 i は、その列の i 番目のディスクに置きます。
- **レイアウト**はシステムレンジに保存し、バージョン番号を持たせます。全ノードが同じレイアウトから同じ配置を計算するので、配置表そのものを配る必要はありません。

### 6.4 ディスク上の形式

- 各ディスクに `blocks/<partition>/<hash 先頭2B>/<blockId>.<shardIdx>` の形でファイルを置きます。ヘッダーには、形式のバージョン、長さ、断片のチェックサムを入れます。
- 書き込み手順: 一時ファイルに書く → `fsync` → `rename` → ディレクトリを `fsync`。
- I/O は `FileChannel` とダイレクトバッファを使い、専用のブロッキングプールで実行します。
- **ブロックごとにファイルを作る方式**から始めます。
  - 小さなファイルの性能が足りなければ、追記型のボリュームファイル（Haystack や SeaweedFS の方式）に切り替えられるように、`BlockStore` trait で抽象化しておきます。

### 6.5 小さなオブジェクトのインライン化

- 閾値（既定 4KiB）以下のオブジェクトは、ブロックに分けず、**メタデータのレコードに直接埋め込みます**。
  - Raft で複製されるので、冗長化はメタデータと同じになります。
  - サムネイルのような、小さなファイルが大量にある使い方で効きます。

### 6.6 書き込みの流れ（PutObject）

```
Client ──PUT──► Gateway (任意のノード)
  1. SigV4 を検証（ストリーミング署名の場合は、チャンクごとに逐次検証）
  2. 認可（キーの権限 + バケットポリシー）
  3. バケットを解決（キャッシュ）→ ストレージクラスと暗号化の設定を決める
  4. 本体をストリームで受け取る:
       - 閾値以下 → メモリに保持してインライン化
       - それ以外 → 4MiB ごとに区切る → (暗号化) → ハッシュ
                    → BlockRefs に intent を登録 → 配置先へ並行して送る
                    → write-quorum に達したら次のブロックへ（並行数には上限を設ける）
                    → 届かなかった断片は修復キューへ
  5. MD5 と追加チェックサムを検証
  6. オブジェクトのレンジのリーダーに、ObjectVersion の書き込みを提案（前提条件付き）
  7. コミットされ適用されたら 200 を返す（ETag、versionId 付き）
```

- 手順 6 が失敗した場合（前提条件が満たされない、など）、書いたブロックは intent の TTL が切れた後に GC で消えます。
- リーダーでないノードが受けた提案は、内部で転送します。レンジの位置情報はキャッシュし、`NotLeader` の応答で更新します。

### 6.7 読み込みの流れ（GetObject）

1. 認証と認可を行います。
2. オブジェクトのレンジで線形化可能な読み込み（ReadIndex）を行い、Head と Version を取り出します。
   - フォロワーでも ReadIndex を使えば読めるので、リーダーに負荷が集中しないようにします。
3. Range 指定を、読むべきブロックと、その中の位置に変換します。
4. ブロックを取得します。
   - **レプリカ**: 近いノードや負荷の低いノードから 1 つ読み、ハッシュを検証します。失敗したら別のレプリカを読みます。
   - **EC**: データ断片を k 個読みます（組織符号なので、そのまま連結するだけです）。欠けていたらパリティを読んで復元します。
5. 必要なら復号し、ストリームで返します。次のブロックを先読みしておきます。

### 6.8 マルチパートアップロード

- 各パートは独立したブロックの列として書き、`Part` レコードを Upload の配下に置きます（オブジェクトと同じレンジです）。
- **CompleteMultipartUpload** は、オブジェクトのレンジで次の処理を 1 つのアトミックなバッチとして行います。
  - パートを検証する
  - `ObjectVersion(body = Parts)` を作る
  - Upload と Part のレコードを消す
  - 使われなかったパートの参照を outbox で外す
- **UploadPartCopy** は、コピー元のブロック参照を範囲で切り出します。ブロックの境目に揃わない部分だけを読み直して、新しいブロックとして書きます。

## 7. クラスタ管理

### 7.1 ブートストラップと参加

```bash
scalas3 cluster init  --name prod --zone dc1          # クラスタ ID、内部 CA、レンジ 0 を作る
scalas3 cluster token create                           # 参加用のトークンを発行する
scalas3 node join --token <t> --seed nodeA:3901        # mTLS の証明書を発行してもらい、参加する
scalas3 layout apply                                   # 必要な場合だけ（既定では自動で適用）
```

- ノード間の通信は、クラスタ内部の CA が発行した証明書を使う **mTLS** で保護します。
- ディスクの追加は、`node disk add` で行うか、設定ファイルで宣言します。

### 7.2 障害検知

- **SWIM 系のゴシップ**で、ノードの生存を把握します（速さ優先で、確定的ではない情報です）。
- **確定的なメンバー情報**は、システムレンジのレイアウトです。
  - 一定時間（既定 30 分）応答がないノードは「down」とみなし、修復を始めます。
  - ノードの「除外」は管理者の操作か自動の方針で決め、レイアウトの変更として提案します。

### 7.3 リバランス

- レイアウトが v から v+1 に変わったら、パーティションごとに新旧の配置の差分を計算します。
  - 新しい配置先は、旧い配置先から断片をコピーします。帯域には上限を設けます。
  - 移行が終わるまでは、**読み込みは新しい配置先 → 旧い配置先の順に試し**、**書き込みは新旧の和集合に**行います。
  - パーティションの同期が終わったら、システムレンジに「完了」を記録します。全パーティションが完了したら、旧いレイアウトを退役させ、不要になった断片を消します。
- **Raft レンジのレプリカの配置**も、同じレイアウトから決めます。Learner を追加し、Joint Consensus で切り替え、旧いレプリカを外します。レンジのリーダーは、ノード間で偏らないように移譲で調整します。

### 7.4 修復とスクラブ

- **スクラブ**: 各ディスクでブロックを定期的に（既定 30 日で一巡）読み、ハッシュを検証します。破損していたら、他の断片から復元して置き換えます。
- **アンチエントロピー**: パーティションごとに「あるべき断片の一覧」（BlockRefs から導出）と「実際にディスクにある一覧」を Merkle 木で比べます。足りないものは補い、余計なものは GC の候補にします。
- 修復キューは、冗長度が低い順（欠けている断片が多い順）に処理します。

## 8. 認証と認可

### 8.1 アクセスキー

- アクセスキー ID とシークレットを発行し、システムレンジに保存します。
  - SigV4 の HMAC 計算には平文のシークレットが必要なので、**マスター鍵で暗号化して**保存します。
- キーごとに、バケット単位の権限（`read`、`write`、`owner`）を付けられます（Garage と同じ考え方です）。
- 管理者のキーは、Admin API 用のトークンとは別に管理します。

### 8.2 バケットポリシー

- AWS のポリシー JSON のうち、よく使われる部分に対応します。
  - `Effect`、`Principal`（アクセスキー、`*`）、`Action`、`Resource`
  - `Condition`: `aws:SourceIp`、`aws:SecureTransport`、`s3:prefix`、`s3:x-amz-server-side-encryption` など
- **評価順**: 明示的な Deny > 明示的な Allow（ポリシー）> キーの権限 > 暗黙の Deny。
- 匿名アクセス（`Principal: *`）は、ポリシーで明示した場合だけ許可します。

### 8.3 CORS と Presigned URL

- CORS: バケットの設定に基づいてプリフライト（OPTIONS）に応答し、レスポンスヘッダーを付けます。
- Presigned URL: SigV4 のクエリ認証に対応し、有効期限は最大 7 日とします。

## 9. 暗号化

| 方式 | 鍵の出所 | 実装 |
|---|---|---|
| SSE-C | リクエストごとにクライアントが鍵を渡す | 鍵の MD5 を検証し、鍵の HMAC だけを保存する。データは AES-256-GCM で暗号化する |
| SSE-S3 | サーバー内のマスター鍵 | エンベロープ暗号化。オブジェクトごとにデータ鍵（DEK）を作り、マスター鍵（KEK）で包んで保存する |
| SSE-KMS | 外部 KMS | v1.x で対応予定。`KeyProvider` trait を通して Vault Transit や KMIP を追加する |

- **ブロック単位で暗号化**します。ノンスは、DEK、オブジェクトのバージョン、ブロックの番号から導きます。こうすると、Range 指定の GET でもブロック単位で復号できます。
- **マスター鍵**は、設定ファイルまたは環境変数で渡します。鍵 ID を持たせてローテーションできるようにし、DEK を包み直すジョブで切り替えます。
- ETag: S3 と同じく、SSE-C を使ったオブジェクトの ETag は MD5 になりません。

## 10. バージョニング、ライフサイクル、クラスタ間複製

### 10.1 バージョニング

- バケットの状態は `Unversioned`、`Enabled`、`Suspended` の 3 つです。
- `versionId` は HLC から作るので、新しい順に並びます。`Unversioned` と `Suspended` のときは `null` 版を上書きします。
- 削除マーカー、バージョンを指定した GET と DELETE、ListObjectVersions に対応します。

### 10.2 ライフサイクル

- 対応するルール:
  - Expiration（日数、日付）
  - NoncurrentVersionExpiration
  - AbortIncompleteMultipartUpload
  - ExpiredObjectDeleteMarker
- **期限切れの処理**:
  - オブジェクトを書くときに、期限切れの予定時刻を RangeLocal の `Lifecycle` 索引にも書きます（同じバッチで書きます）。
  - 各レンジのリーダーが、時刻の順に走査して削除を提案します。
  - ルールを変えたら、該当するバケットの索引を作り直すジョブを流します。

### 10.3 クラスタ間の非同期複製

- S3 の `PutBucketReplication` と互換の設定で、**別の S3 互換エンドポイント**（別の scalas3 クラスタや AWS S3 など）へ複製します。
- **変更の流れ**:
  - オブジェクトを書いたときに、outbox に「複製対象の変更」を記録します。
  - レプリケーションワーカーが、その変更を S3 プロトコル（SigV4 クライアント）で相手先に PUT または DELETE します。
- 状態を `x-amz-replication-status`（PENDING、COMPLETED、FAILED）で返します。
- 双方向の複製は v1.0 では対象外です（一方向のみ）。

## 11. ノード間プロトコル

- fs2-io の TCP と TLS（mTLS）の上に、**独自のフレーミング**を載せます。
  ```
  Frame = [len u32][streamId u32][kind u8][flags u8][payload]
  kind  = Request | Response | StreamData | StreamEnd | Cancel | Ping
  ```
- **1 本の接続を多重化**します。
  - 優先度の高いクラス（Raft のハートビート、投票）と、大量データのクラス（ブロックの転送）で送信キューを分けます。こうすると、大きな転送のせいで Raft が遅れることがありません（head-of-line blocking を避けます）。
- **バックプレッシャー**: ストリームごとにクレジット制のフロー制御を行います。
- メッセージは scodec でエンコードし、バージョン番号を付けます。互換性の方針は、「1 つ前のマイナーバージョンとは通信できる」とします（ローリングアップグレードのため）。
- `Transport` trait を通して使うので、シミュレーションでは SimNetwork に差し替えられます。

## 12. 運用

### 12.1 Admin API と CLI

- Admin API は tapir で定義し、OpenAPI 3 を生成します。S3 とは**別のポートで、別のトークン**で認証します。
  - クラスタの状態、ノードとディスク、レイアウト、アクセスキー、バケット、ストレージクラス、修復とリバランスの進捗、レンジの一覧を扱えます。
- CLI（`scalas3`）は、Admin API のクライアントとして作り、native-image で配布します。
- Web UI は v1.x 以降で、この OpenAPI の上に作ります。

### 12.2 監視

- otel4s でメトリクスとトレースを取ります。
  - Prometheus 用の `/metrics` を公開し、OTLP にも出力できるようにします。
- 主なメトリクス:
  - S3 操作ごとのレイテンシーとエラー率
  - Raft のコミット遅延、リーダーの交代回数
  - LSM のコンパクションの遅れ
  - ディスクの使用率、I/O エラー
  - 修復キューの長さ、冗長度が下がったブロックの数
  - リバランスの進捗、GC の積み残し
- ヘルスチェック: `/health/live` と `/health/ready` を用意します。ready は、担当するレンジが使える状態かを見ます。

### 12.3 配布

- JVM 版: fat jar と、Docker イメージ（distroless と JRE 21 以降）を用意します。
- Kubernetes: Helm チャートと StatefulSet を用意します。Operator は v1.x 以降に検討します。
- ベアメタル: systemd の unit と、tarball を用意します。
- native-image: CLI を主に配布します。サーバーの native 版は、CI でビルドを保証し、小さなノード向けの「実験的」な成果物として出します。

## 13. テスト戦略

| 層 | 手法 | 対象 |
|---|---|---|
| 単体 | munit と ScalaCheck（プロパティテスト） | コーデック、キーのエンコード（順序を保つか）、Raft コアの状態遷移、LSM のマージ、配置計算、SigV4、ポリシー評価 |
| モデル検査 | TLA+ と TLC | Raft の変更点（ログの共有、適用とフラッシュの関係、Joint Consensus）、「ブロックの永続化 → メタデータのコミット」の不変条件、GC と intent、リバランス中の読み書き |
| 決定的シミュレーション | TestControl、SimNetwork、SimDisk | 複数ノードのクラスタを 1 つのプロセスで動かします。シード値から、ネットワークの分断、遅延、メッセージの欠落や順序の入れ替え、プロセスのクラッシュ、fsync の消失、書き込みの途中切れを注入し、線形化可能性と耐久性を検査します |
| 線形化可能性の検査 | Jepsen（Elle と Knossos） | 実際のクラスタ（Docker や VM）に S3 API 経由で負荷と障害を与え、履歴を検証します |
| S3 互換 | Ceph の s3-tests、AWS SDK（Java、Go、Python、PHP）、rclone、MinIO の mint | CI で毎回実行します。結果を一覧にし、互換の状況を公開します |
| 性能 | warp、および s3-benchmark 系 | Garage や MinIO と同じ条件で比べます。リグレッションも検出します |

**シミュレーションを可能にするための約束事**（§4.1 を再掲します）:

- 時刻、乱数、I/O は、すべて `runtime` の trait を通します。
- スレッドプールに頼った並行処理（`evalOn` の乱用など）を、ドメインのコードに書きません。
- `ConcurrentHashMap` のような、結果がスケジュールに依存する構造は使わず、`Ref` を使います。

## 15. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| 自前の Raft と LSM に不具合が潜む | データの消失や不整合 | 純粋なコアと決定的シミュレーションを最優先し、TLA+ と Jepsen で検証する。M1 と M2 の完了条件を厳しくする |
| 範囲が大きく、v1.0 までの期間が長い | 実際に使えるまで時間がかかる | M4 の時点で「1 ノードで実際に使える」状態を作り、実際に使いながら進める |
| JVM の性能（GC、ファイルの I/O、Ember の性能） | 性能目標（G6）を達成できない | ダイレクトバッファ、オブジェクトの使い回し、ZGC を使う。HTTP サーバーは差し替えられるようにしておく。M4 からベンチマークを CI に入れる |
| ブロックごとにファイルを作ると、小さなファイルの性能が出ない | ファイル数が膨大になる | インライン化（§6.5）で緩和し、`BlockStore` を抽象化しておく。追記型のボリュームファイルに移れるようにする |
| レンジをまたぐ処理が結果整合になる | 参照数や孤児の扱いが複雑になる | outbox と猶予期間付きの GC で対処し、不変条件を TLA+ で検証する。必要になれば v1.x でトランザクションを導入する |

### 運用上の注意（EC）

- EC で m 台の故障に耐えたいなら、メタデータの複製数（`SCALAS3_REPLICAS`）も 2m+1 以上にすること。メタデータが先に過半数を失うと、データが残っていても読めない（4+2 なら 5）。
- ノードが k+m 台より少ないと、断片を同じノードに重ねて置くので、耐えられる故障の数は減る。

### 実装の要点

- **障害ノードの検知**（C10、`Health`）：Down と分かっているノードへの書き込みは飛ばす。応答のないノードを待つと、過半数に届いていても RPC のタイムアウトまで止まるため。
- **機能の水準**（`Health.Features`）：死活確認の応答（health.ping2）で、相手の版が対応している機能の水準を伝える。古い版は UnknownMethod を返すので水準 0。レンジの統合（水準 1）は、全ノードが水準 1 以上と分かるまで始めない（古い版は Freeze と Merge のコマンドを読めず、レプリカが止まるため）。docs/upgrade.md。
- **RPC のタイムアウトと書き込みの過半数**：RPC は 1 回 15 秒・接続 5 秒でタイムアウトし、タイムアウトした接続は捨てる。ブロックと EC の断片の書き込みは、過半数に届いた時点で返す（`Quorum`。残りは裏で書き終える）。
- **一時的な失敗**：止まったノードへの RPC の失敗（切断、時間切れ、接続できない）は 503 にする。メタデータの読み込みは時間切れでもやり直し、効いたか分からない書き込みは 503 で返す。応答の本体を作る途中の失敗は、まだ何も送っていなければ 500 を返し、警告をログに残す。
- **リーダーの偏りの是正**（`RangeManager.balanceLeaders`）：各ノードは手元のレプリカから、どのノードが何個のレンジのリーダーかを数える。自分の受け持ちが最少のノードより 2 以上多ければ、追いついている投票メンバーに 1 つ譲る（1 回の管理作業で 1 つ）。レプリカの入れ替えの途中（または入れ替えるべきレンジがある間）は譲らない。
  - リーダーが外される側（Draining）なら、構成を変える前に、残るメンバーへリーダーを譲る。
  - 初期レンジ（0 と 1）も、分割で生まれたレンジと同じく初期位置を 5 にする。新しく加わったレプリカがスナップショットで追いつき、ログを通さずに書いた記述子を受け取れるようにするため。
- **追記型のボリューム**（D6、`VolumeStore`）：ブロックと EC の断片を、ディスクごとの大きなファイルに追記する。
  - **索引**：場所と最後に使われた時刻は、ディスクごとの LSM に持つ。どこまで索引に入れたかを同じ書き込みで記録し、起動時はそこから先を読み直す（読み直すときは、索引のキーをコピーして記録のバッファを留めない）。止めるときは索引を書き出す。
  - **書き込み**：1 本のファイバーがまとめて追記し、fsync を 1 回にする。
  - **削除と回収**：削除は索引から外すだけ。GC の後、ゴミが半分以上のボリュームは生きている値を写して消す。写すときは、索引がまだ同じ場所（ボリュームと位置）を指しているかだけを比べ、時刻は新しい方を残す（時刻まで比べると、写している間の重複排除や touch で写し損ね、ブロックを失う）。消したボリュームはディレクトリを fsync してから、読み直しの位置の記録を消す（逆だと電源断の後に消した値が生き返る）。
  - **GC との関係**：索引の時刻の更新は落ちると失われうるので、起動から猶予期間が過ぎるまでは GC で消さない。
  - **既存データ**：ブロックごとのファイル（以前の形式）は起動時に移す。
- **長いアップロードの GC 保護**（`DataPath`）：アップロード中は、書いたブロックの更新時刻を GC の猶予期間の 1/3 ごとに進め直す。長くかかったアップロードは、コミットの直前にブロックが残っているか確かめる（C3）。
- **スナップショットのストリーム送信**（`RaftNode`、`RangeStateMachine`）：
  - **送る側**：リーダーは、適用位置と揃えた LSM のビューを取り、約 512 件ずつのかたまりを裏で順に送る（相手ごとに 1 本、ノード全体で同時に 2 本まで）。
  - **受ける側**：かたまりを、レンジの区間の外の預かり（`Keys.staging`）に置き、元のデータには触れない。揃ったら「切り替え中」の印を永続化してから、元のデータを消して預かりから写す。
  - **途中で落ちたとき**：転送の途中なら元のデータが残る。切り替えの途中なら、起動時に印を見てやり直す。取り込みを永続化してから Raft のストレージを書き換え、間で落ちても状態マシンが記録したスナップショットの位置（`SnapMeta`）から再開する。
  - **ノード全体の上限**：同時に扱えるのは送信 2 本・取り込み 1 本まで。多数のレンジで一斉にビューを握ると、memtable が留まってヒープを使い切るため。
  - **ログを残す相手**：リーダーは、最近応答のあったフォロワーのためだけにログを残す（上限 32 MiB）。止まっているフォロワーのために全レンジでログを残すと、ヒープを圧迫するため。
  - **止まったグループの扱い**：イベントループが例外で止まったグループは、管理処理がストレージと状態マシンから起動し直す。
- **レンジの統合**（`RangeManager.maybeMerge`、`Command.Freeze` と `Command.Merge`）：隣り合う 2 つのレンジの中身の合計が `mergeBytes`（既定 2 MiB。分割の大きさの 1/4 を超えない）以下になったら、1 つにまとめる。大量に削除した後に、小さなレンジ（それぞれが Raft のグループ）が残り続けないようにするため。
  - **手順**（左のレンジのリーダーが管理作業のたびに進める）：
    1. 右隣を探す。右が凍結されていなければ、両方の中身が小さく、投票メンバーが同じで、構成の変更の途中でないときだけ、右に `Freeze` を提案する。
    2. 右が凍結されていれば、右のリーダーから中身を読み（ReadIndex を通す）、左に `Merge`（右の記述子と中身）を提案する。
    3. 広げた記述子を公開し、右の記述子をシステムレンジから消す。
  - **凍結**：凍結したレンジは読み書きと分割を拒否する（クライアントは区間外の応答を受けて記述子を読み直し、統合後の左に送り直す）。凍結した後は中身が変わらないので、読み出した中身が最終の状態になる。凍結は取り消さない。取り消せるようにすると、左が引き継いだ後に右が書き込みを受け、同じキーを 2 つのレンジが持つおそれがあるため。代わりに、統合が終わるまで、右の左隣にいるレンジのリーダーが（途中でリーダーが替わっても、左が分割されて別のレンジになっても）続きを進める。凍結の印はスナップショットにも含まれるので、新しく加わったレプリカも凍結を知る。
  - **中身をコマンドで運ぶ**：各ノードの右のレプリカの進み具合は違う（遅れていることも、無いこともある）ので、左は手元のデータに頼らず、コマンドに含めた中身で右の区間を置き換える。こうすると左のどのレプリカでも同じ結果になる（状態マシンの決定性）。そのぶん、右の中身は 1 つの Raft のエントリに収まる大きさに限る。
  - **右のレプリカの片付け**：左が `Merge` を適用するときは、まず手元の右のレプリカを止め、レンジ固有のキー・預かり・Raft のログを消してから（区間のデータは残す）、区間を置き換える。止めないと、遅れて動いている右が後から古いデータを書き込んだり、スナップショットを取り込んで区間を消したりする。途中で落ちても左の適用位置が進んでいないので、起動後にもう一度適用する（何度行っても同じ結果になる）。左のないノードに残った凍結したレプリカは、システムレンジから記述子が消えたら片付ける。
  - **記述子の選び方**：統合後の左の世代は、左と右のどちらよりも大きくする。クライアントは重なる記述子のうち世代の大きいほうを選ぶので、右の古い記述子が残っていても左に送る。
- **分割前の古いレンジへの区間外の書き込み**：適用時に拒否する（`RangeStateMachineSuite`）。クライアントは記述子を読み直してやり直す。
- **公開ポートの HTTPS**（`PublicTls`）：PEM の証明書と鍵を渡すと、Netty のサーバーが TLS を受ける。更新されたファイルは 1 分ごとに読み直す（鍵と証明書が対になっていなければ前のものを使い続ける）。docs/tls.md。
- **小さな本文の検証**：設定の XML・JSON、DeleteObjects、CompleteMultipartUpload の本文は 2 MiB を上限に読み、署名した SHA-256、Content-MD5、追加チェックサムを確かめる。
- **ノード間証明書の自動更新**（C14）：有効期間の 2/3 で発行し直す。CA を持つノードは自分で、ほかのノードはいまの証明書で相互認証して参加の受け付けの `/v1/renew` に頼む。TLS の層は鍵ストアの更新を 1 分ごとに見て読み直す（手で差し替えた鍵ストアにも効く）。docs/tls.md。

### シミュレーションの決定性

- すべてのシミュレーションを `Sim.run` で動かし、種を必ず指定する。cats-effect の TestControl は、同じ時刻に実行される処理の順序を乱数で入れ替えるため。既定は固定で、`SCALAS3_SIM_SEED` か `-Dscalas3.sim.seed` で変えられる。失敗時は種を表示する。
- RaftNode は送信処理を自分で持ち、ノード ID の順に取り消す（Supervisor に預けると、取り消しの順序がオブジェクトのハッシュに依存する）。
- `DeterminismSuite`（S3 層まで含む）と `RaftDeterminismSuite` が、同じ種で動かしたときにネットワーク上のやり取りが完全に一致することを検査する。
- 種を変えながら回すことで、いろいろな実行順を試せる（CI では種を変えて回すとよい）。

### 検証の手段

- **TLA+**：`spec/BlockGc.tla`（GC と重複排除・共有・長いアップロードの競合）。詳細は spec/README.md。
- **線形化可能性**：`sim/Linearizability`（Wing-Gong-Lowe）と `LinearizabilitySimSuite`（分断・電源断・分割・統合の下で、読み・書き・CAS の履歴がキーごとに線形化可能か）。
- **実クラスタでの障害試験**（`FaultCheck`、server のテスト側）：podman で 3 ノードを動かし、kill・一時停止（SIGSTOP）・ネットワークの切り離しを入れながら、CAS 付きの読み書きを流して線形化可能性を確かめる。
- **長時間の負荷**（`S3Soak`）：PUT・GET・DELETE を混ぜて流し続け、中身とエラーを数える。docs/benchmark.md。
- **ローリングアップグレード**（`UpgradeCheck`、`it/upgrade/run.sh`）：docs/upgrade.md。

### 残っている課題

- **証明書の失効**（ノード間）：CRL はない。取り外したノードの証明書は期限まで有効で、受け付けで更新もできる（docs/tls.md）。CA の更新もない。
- **複数のマシンでの検証**：性能、障害試験、アップグレード（M9 の完了条件）は、まだ 1 台のマシンの中でしか確かめていない。実際の Jepsen（Clojure、実クラスタ）も使っていない。
- **Helm チャート**：1 ノードの kind でしか確かめていない。実際の複数ノードの Kubernetes、負荷をかけた状態、ノードの入れ替えは未確認。
- **GC の形式検証**：spec/BlockGc.tla はボリュームの詰め直しを扱っていない。
